RAG Collapse · HotpotQA · Cross-Model Baseline

One model reads the documents another model wrote

The cross-model-baseline experiment asks a simple question the standard self-refinement loop can't: does a model collapse the same way when the documents it reads each round are synthesized from a different model's answers? A main model (measured) and a side model both answer from the same context, but only the side model's answers become the next round's documents — so the main model is a probe reading a stream it never wrote. This page covers the design, the exact wiring, and the GPU-scheduling hack that finally got it to run on Unity.

main = the measured model (Qwen2.5-14B) side = writes the documents (DeepSeek-R1-7B) doc-gen = turns answers into documents

01 — Background

RAG collapse, and a question it can't answer alone

RAG collapse is what happens when a retrieval-augmented model feeds on its own output: it answers from retrieved context, those answers are turned into "documents," those documents become the next round's context, and over many rounds the answers lose diversity and drift. The repo's baseline measures exactly this self-consuming loop for one model under three document-update rules (replace-all, replace-one, search).

But the baseline conflates two things: the model that answers and the model whose answers become the documents are the same. So you can't ask: is collapse a property of the model doing the reading, or of the document stream it's fed? If model A reads a stream of documents written from model B's answers, does A still collapse — and toward what?

The cross-model-baseline isolates the reader from the writer. Two answer models run each round on the same context; only the side model's answers are turned into documents; the main model reads them and is the one we measure. The main model never writes the stream — it's a pure probe.
02 — The baseline it extends

The two-model self-refinement loop

The DeepSeek / graphite baseline (pipeline.py, launched by scripts/deepseek_baseline/) already runs two models in different roles:

Answer model

Answers each question from the current documents (num_runs = 10 samples per question per round). Its answers are what we measure for collapse, and what get turned into the next round's documents.

Doc-gen model

A separate Qwen2.5-7B-Instruct server (served qwen2.5-7b-doc) that rewrites each answer into a naturalistic "document" for the next round. Fixed across all arms.

The loop is answer → doc-gen → next-round context → answer … over 10 / 20 / 30 rounds (replace-all / replace-one / search). The seam where answers become documents lives at pipeline.py:888–897.

03 — The cross-feed

Side writes the stream; main reads it

The cross-model-baseline adds a second answer model ("side") and re-sources the document stream from it. One-directional, single shared stream:

each round r
Both models answer

main and side both answer from the same current_docs (10 runs each).

→
measured
Keep main's answers

main's 10 answers are stored (answer) — this is the collapse signal we track.

→
the cross-feed
Side → doc-gen

the side model's answers (not main's) go to the doc-gen model → documents.

→
round r+1
Both read the new docs

those documents become the next context that both models read again.

What this means. The document stream is effectively the side model self-refining (its answers → docs → it reads them again), while the main model is a passenger reading that same stream and being measured. Main's answers are recorded too (as side_answer's counterpart) but never feed the loop. So we measure whether Qwen-14B collapses when fed a DeepSeek-driven document stream.

Both models read the identical context each round (the same documents, built from the side model), so the only difference between them is the model itself — a clean A/B of reader vs. writer.

04 — What changes in code

One new answer model, one routing switch

The change mirrors the existing --doc-model-* wiring (and the hotpot distractor_llm precedent). It is fully backward-compatible: with no --side-model-* flags, pipeline.py behaves exactly like today's baseline.

  • New flags — --side-model-mode/-name/-vllm-api-base (+ temperature / max-tokens / top-p, inheriting the main values when unset), and --docs-from-side.
  • Build a second answer model — side_llm via build_llm(...), alongside the main llm and the doc_llm.
  • Answer loop — after main's llm.inference_batch(...), run the same batch through side_llm.inference_batch(...); store both answer and side_answer per run.
  • Re-source the doc seam — at pipeline.py:888–897, when --docs-from-side is set, the documents are built from per_question_side_answers instead of the main answers.
  • Metadata — records side_model, side_model_mode, docs_from_side. Guard: --docs-from-side requires a side model and is rejected for the agentic_rag variant.
# pipeline.py answer loop — both models read the SAME batch_conversations
all_answers      = llm.inference_batch(batch_conversations)          # main (measured)
if args.docs_from_side and side_llm is not None:
    all_side_answers = side_llm.inference_batch(batch_conversations) # side (writes the docs)
...
# Step 3 — the doc seam, now sourced from the side model
answers = per_question_side_answers[i] if per_question_side_answers else per_question_answers[i]
convos  = [get_create_document_conversation(question=..., answer=ans) for ans in answers]
all_doc_texts = doc_llm.inference_batch(convos)

06 — The run hack ★

Getting 3 GPU servers to actually schedule

The design needs three independent vLLM servers (main, side, doc-gen), each on its own GPU. On Unity that turned out to be the hard part — the full run failed to start five times before it ran. Here's the whole debugging arc, because the fixes are reusable.

Symptom: the doc-gen server never scheduled

Every attempt, the main + side servers came up within minutes, but the third server (doc-gen) sat PENDING (Priority) until the launcher's wait window expired and scancelled everything. sacct showed it never ran (00:00:00 elapsed). The cluster had 387 pending vs 179 running GPU jobs — heavily oversubscribed.

Fix 1 — stop asking for premium GPUs the 7B doesn't need

The doc-gen server requested --constraint=vram48|vram80 (A100 / L40S / A40) — the most contended pool. But the doc model is a small Qwen2.5-7B (~15 GB bf16) that fits on a 24 GB card. First broadening to vram23|vram32|… made it schedule — onto an ancient M40 (Maxwell, sm_52), where vLLM crashed:

CUDA error: no kernel image is available for execution on the device  # M40, gypsum-gpu008

The fix that stuck: require the bf16 feature. Every bf16-capable node here is modern and ≥24 GB (L4 / L40S / A40 / A100 / H100), so this opens the abundant, idle L4 pool while excluding the M40 / V100 / Turing cards that can't run a bf16 model.

# scripts/hotpot-misinfo/server_docgen.sh
#SBATCH --constraint=bf16   # was vram48|vram80 (premium-only) → starved on (Priority)

Fix 2 — the real unlock: drop to 2 GPUs (DOC_ON_MAIN)

Even eligible for far more GPUs, getting three concurrent GPUs on the oversubscribed cluster kept failing — a long-walltime job is hard for Slurm's backfill to slot in, and the 3rd server stayed behind hundreds of higher-priority jobs. So the launcher gained an DOC_ON_MAIN=1 mode (Option B): run document generation on the main server instead of a separate doc-gen GPU. The run then needs only two concurrent GPUs (main + side), which schedule reliably.

Trade-off (recorded in metadata). With DOC_ON_MAIN the document-writer becomes the main model (qwen2.5-14b) rather than the dedicated qwen2.5-7b-doc. The cross-feed is unchanged — DeepSeek's answers still become the documents — only the rewriter model differs. experiment_metadata.doc_model reflects whichever was used.

Fix 3 — shorter walltime for friendlier backfill

The 48-hour servers (the max submittable) were the hardest to schedule: backfill won't place a 2-day job onto a GPU reserved for a sooner higher-priority job. Dropping to 24 h servers / 23 h clients made placement much easier while still covering the run. (The earlier 20-question smoke scheduled fine precisely because its 3-hour servers were backfill-friendly.)

Two more launcher robustness fixes from the saga

  • Wait window 50 min → 5 h. The launcher's WAIT_TRIES default was too short for a 3rd GPU under load, so it timed out and scancelled the two servers that had come up. Raised to 5 h (matching the distractor launcher).
  • Valid feature tokens. An intermediate fix used vram24, which is not a real Slurm feature on this cluster (valid: vram8/11/12/16/23/32/40/48/80) → Invalid feature specification rejected the sbatch outright.
Net result. bf16 doc-gen + DOC_ON_MAIN=1 + 24 h walltime → the full run schedules on 2 GPUs and runs to completion. The 3-server path is kept (default) for when the cluster is quiet.
07 — How to run it

Running the experiment

Full run (2-GPU mode — recommended on a busy cluster)

# login node. main + side GPU servers; doc-gen runs on the main server (no 3rd GPU).
DOC_ON_MAIN=1 MAX_Q=400 MAX_ITERS=30 SERVER_TIME=24:00:00 CLIENT_TIME=23:00:00 \
  bash scripts/cross_model_baseline/launch_cross_model_baseline.sh

MAX_ITERS=30 uncaps the per-variant rounds (min(variant_rounds, 30) = 10 / 20 / 30). Omit DOC_ON_MAIN for the original 3-server design (needs a 3rd bf16 GPU). The launcher starts the servers, waits up to 5 h for them to serve, fans out one CPU client per variant, and submits an afterany reaper that scancels the servers when the clients finish.

Smoke (cheap end-to-end check)

MAX_Q=20 MAX_ITERS=2 SERVER_TIME=03:00:00 CLIENT_TIME=02:00:00 \
  bash scripts/cross_model_baseline/launch_cross_model_baseline.sh

One variant (what the client expands to)

python -u pipeline.py \
  --model-mode server --vllm-api-base http://<main>/v1 --model-name qwen2.5-14b \
  --side-model-mode server --side-vllm-api-base http://<side>/v1 \
  --side-model-name deepseek-r1-distill-qwen-7b --side-max-tokens 4096 --docs-from-side \
  --doc-model-mode server --doc-vllm-api-base http://<doc-or-main>/v1 --doc-model-name qwen2.5-7b-doc \
  --dataset-path datasets/umass_data.entity.chatgpt.400.jsonl --num-runs 10 --chars-per-doc 400 \
  --pipeline-variant hybrid --num-synth-docs 10 --num-db-docs 0 --max-iterations 2 \
  --output-path .../local_replace_all.json
08 — What we measure

Collapse on the main model

Because the output schema is unchanged (main's answers live in answer), the existing metric pipeline applies with no eval changes: evaluation.py (ROUGE / TES / cosine, unique words, same-answer) and entity_extraction.py (unique entities, entity similarity) read answer = the main model. The headline comparison is main's collapse trajectory when fed a DeepSeek-driven stream vs. the Qwen-14B self-loop baseline — same metrics, same dataset, same rounds.

The extra side_answer field lets you also measure the side model's own self-loop (the stream's author), and compare reader vs. writer round-by-round.

09 — Smoke validation

The wiring, verified end-to-end

A 20-question, 2-round smoke confirmed the cross-feed is correct before the full run: all 3 variants finished with 0 errors; metadata showed model=qwen2.5-14b, side_model=deepseek-r1-distill-qwen-7b, docs_from_side=true; and every run carried both answers. The two models are visibly different — direct evidence that the side model drives the docs:

main · answer (measured) Jalaiah Harmon, Niana Guerrero, Mackenzie Ziegler, Katie Feeney, Charli D'Amelio…
side · side_answer (→ becomes the document) "The most popular TikTok dancers, based on follower counts and mentions, include…"

Main returns terse entity lists; DeepSeek returns prose — and it's DeepSeek's prose that gets rewritten into the documents Qwen-14B then reads. The full 400-question run (10 / 20 / 30 rounds) runs on the 2-GPU configuration described in §6.
